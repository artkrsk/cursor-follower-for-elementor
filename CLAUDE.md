# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Arts Cursor Follower for Elementor": a zero-runtime-dependency TypeScript cursor engine (`src/ts/` + `src/styles/`) inside a deliberately thin WordPress plugin shell (`src/php/`, `src/wordpress-plugin/`).

- **No backward-compatibility requirements.** This repo defines the contract outright — markup shape, class names, attributes and defaults are whatever `core/markup.ts` and `core/options.ts` say — and Velum integrates against that. There is no prior release to stay compatible with, so a change here needs no migration path, only a reason.
- **The PHP layer is live and deliberately thin.** The main plugin file bootstraps `src/php/Plugin.php`, which prints the inline `wp_head` gate (the plugin's only front-end output — nothing is enqueued; see the loading model under Architecture), carries `window.artsCursorFollowerOptions` in that same block (inline JSON, not `wp_localize_script`), and wires the Elementor Site Settings tab + editor live bridge. It also injects a per-widget "Cursor Effects" section into a curated set of widgets (`src/php/Elementor/WidgetControls.php`), whose values reach the engine only through channels the editor replays — see **Elementor integration — landmines** below before touching any of it. There is intentionally NO PHP markup printer — the engine builds its own DOM client-side, always: device capability gates the pointer listeners and CSS visibility, not the markup. The engine is also consumed outside WordPress via composer symlink (velum-core), which is why the PHP layer stays thin.

## Commands

- `pnpm dev` — VitePress dev server (port 5200) for the public docs site at `docs/`, which doubles as the browser harness: the engine boots live on every page (theme `Layout.vue`) and the demo pages exercise real layout, real hit-testing and the CSS state machine — still the only harness for anything unit tests structurally cannot reach. `pnpm exec vitepress build docs` / `preview docs` build and serve the static site.
- `pnpm dev:plugin` — watch-compile the engine bundle + CSS into `src/php/libraries/cursor-follower-for-elementor/` and, when `DEV_TARGET` is set in `.env`, mirror the plugin into a LocalWP site.
- `pnpm build` — release build: stamps versions, bundles minified JS/CSS, stages `dist/cursor-follower-for-elementor/`, zips, runs release assertions. Stamping rewrites tracked files (plugin header, readme.txt, package.json).
- `pnpm exec tsc --noEmit` — typecheck (esbuild does not type-check)
- `pnpm test` / `pnpm test:coverage` (`pnpm exec vitest` to watch) — Vitest over `tests/**/*.test.ts`. Config is `vitest.config.ts`; the docs site's Vite config lives inside VitePress (`docs/.vitepress/config.mts`), which also re-declares the `@engine`/`@styles` aliases for the browser build.
- `pnpm exec biome check .` / `biome format --write .` — Biome, scoped to `src/ts/**`, `tests/**`, the docs TS (`docs/.vitepress/**/*.ts`, `docs/demos/**/*.ts`) and root configs. SCSS goes through stylelint instead (`pnpm exec stylelint 'src/styles/**/*.scss'`, config extends the `@arts/wp-plugin-tooling` base); `.vue` files are not linted or formatted by anything.
- `pnpm exec knip` / `pnpm exec fallow` — two static analyzers over the same ground (unused files, exports, dependencies; fallow adds circular-dependency and boundary passes). `pnpm fallow` passes no subcommand, which is how fallow runs all three of dead-code + dupes + health together; `fallow dead-code` is the fast subset when only the unused-code half matters. Both exit non-zero on findings. They are deliberately redundant so each cross-checks the other, which matters because their scopes differ: the build runner lives in `@arts/wp-plugin-tooling` (external package), so neither tool scans build code anymore.
- `pnpm test:coverage && pnpm exec fallow health --coverage coverage/coverage-final.json` — the complexity/CRAP half on *fresh* coverage. `pnpm fallow` reaches the same analysis but never regenerates it: fallow auto-discovers `coverage/coverage-final.json` when it happens to be on disk, so CRAP there is computed against whatever the last `pnpm test:coverage` left behind, and silently falls back to estimation when the file is absent. This script regenerates coverage first and passes it in: fallow's CRAP is otherwise `static_estimated`, where a module counts as covered the moment any test file has a dependency path to it — a token import satisfies it and the score stops meaning anything. fallow's `--coverage` reads Istanbul-format `coverage-final.json` — which Vitest's `v8` provider now emits (AST-remapped since Vitest 3.2; verified 2026-08-13, v8 matched one more function than the istanbul provider), so the shared config's v8 default is fine here. Findings whose cyclomatic and cognitive numbers are both under threshold are pure coverage artefacts — write the test, don't reshape the function.

**Hooks and CI.** `lefthook.yml` (wired by `package.json#prepare`, so `pnpm install` is all it takes) installs two gates. `pre-commit`: three autofixers that rewrite and re-stage the staged files (`stage_fixed`) — Biome, stylelint on `src/styles` SCSS, phpcbf on `src/php` — then typecheck; sequential, because each check has to read what the autofix produced. `pre-push`: the full Vitest run, PHPStan, phpcs. The GitHub Actions workflows are thin callers of the reusable ones in `artkrsk/wordpress-plugin-workflows`: `test.yml` (lint, typecheck, test, PHPStan; plus a build, a zip size budget and the WordPress.org Plugin Check against `dist/`), `deploy-docs.yml` (VitePress to Pages), `canary.yml` (weekly), a scheduled WordPress version checker, and `release.yml`, which fires on a `v*` tag. That last one deploys to WordPress.org over SVN (`deploy_to_wordpress: true`; the SVN secrets are account-wide — see the folder CLAUDE.md), and only the jobs in our own files are `self-hosted` (the reusable workflows pin `ubuntu-latest` internally, which the caller cannot override).

Everything else runs `self-hosted` on the shared Raspberry Pi (arm64), one runner service per repo. Three consequences worth knowing before editing a workflow: the `pnpm/action-setup` / `setup-node` / `setup-php` steps are gated on `runner.environment == 'github-hosted'` because the host already has all of it on PATH (its `pnpm` is corepack-shimmed, so `packageManager` is honoured without any setup step); Plugin Check must take the cross-repo wp-env host lock (it ships with the reusable workflows in `wordpress-plugin-workflows`), since `concurrency:` only serializes within one repo while every repo here has its own runner and they collide on wp-env's ports; and the host sets `core.hooksPath` to `/dev/null` globally, which `lefthook install` refuses to run against — that is why `prepare` skips when `CI` is set.

Versioning: the `version` field in `composer.json` is the single source of truth. `arts-wp` stamps it into the plugin header, `ARTS_CURSOR_FOLLOWER_PLUGIN_VERSION`, `readme.txt`, and `package.json` on every dev/build run — never hand-edit the version anywhere else.

## Architecture

`src/ts/core/createCursor.ts` is the composition root that wires everything. `src/ts/index.ts` is the library surface; `src/ts/boot.ts` is the WordPress entry (side-effect IIFE, built by `@arts/wp-plugin-tooling` (`arts-wp` — build/release/changelog/blueprint/doctor mechanics are documented in that package, not here)).

**Loading model.** `src/ts/gate.ts` is the second build entry: a ~1KB pre-paint loader PHP prints inline on `wp_head` (nothing is enqueued on the front end). It installs `window.artsCursor` at parse, predicts the `<html>` classes from the shared `POINTER_MEDIA_QUERY`, and injects the CSS `<link>` then engine `<script>` (ids `arts-cursor-follower-for-elementor-css/-js`, CSS serialized before JS) on the first mouse/pen `pointermove`, `wheel`, or media-query flip to matching — so touch devices download zero engine bytes. `boot.ts` claims the gate's pending `ready` resolver (`ready` may resolve late or never — never `null`); the Elementor preview loads immediately via the `editor` flag in `window.artsCursorFollowerBoot`. The printed gate tag carries NO id on purpose (ArtsAJAXTransitions re-executes id'd head scripts every transition), and the whole block is marked for cache-plugin opt-outs (noptimize comments, `data-no-optimize`, `data-cfasync`, `nowprocket`). Full rationale: `docs/superpowers/specs/2026-07-26-conditional-loading-design.md`.

**Frame path** (allocation-free by design — preallocated vectors mutated in place):
pointer input (`core/input.ts`, gated by a `(hover:hover) and (pointer:fine)` media query that owns listener lifecycle) → `IFrameState` (built by `core/frameState.ts`) → lerp + lag (`follower/pipeline.ts`) → elastic squash (`follower/elastic.ts`) → transform writer (`follower/transformWriter.ts`: one `transform` value mutated via CSS Typed OM, string fallback on Firefox). The rAF ticker (`core/ticker.ts`) runs only while subscribed; the engine sleeps by unsubscribing once converged and wakes on pointer activity (`wake()`/`sleep()` on `follower/motion.ts`'s system, driven from the composition root).

**Two coordinate spaces — the core invariant.** Free-roam runs in viewport space (scroll never drags the cursor off the pointer). Magnetic engagement (`effects/magnetic.ts`) switches composition to page space, and scroll is subtracted at render time, outside the lerp — that is what keeps the cursor glued to its anchor while the page scrolls. Engage/release add/remove the scroll offset on `state.follower` so the space switch never jumps visually.

**Visual effects are a CSS state machine.** JS (`effects/suite.ts`) only flips `data-cursor-*` attributes and sets custom properties; all animation is CSS transitions inside the `arts-cursor` cascade layer (so unlayered theme CSS wins by default). Effect state is computed from layers: the transient hover payload at the bottom, programmatic sessions stacked above, last-wins per key; any layer change triggers one recompute of the merged payload — no sticky flags.

Supporting modules:
- `interaction/targets.ts` — delegated pointerover/out, one `resolveTarget()` pass shared by both handlers so enter and leave always compare the same element, per-element JSON payloads (`data-arts-cursor-follower-target`) parsed once into a WeakMap. A rule matched on an ancestor never outranks a target that is itself interactive (`a`, `button`, `[role="button"]`, opt-in class) — only a rule naming the element itself can claim it, else it gets the bare-interactive highlight; this is what keeps a carousel's track-wide drag rule off the links nested in its slides.
- `interaction/geometry.ts` — page-space element geometry with no layout flushes on interaction paths (IntersectionObserver revalidation, ResizeObserver, idle pre-warm). Entries are stable objects mutated in place. One deliberate exception: magnetic engage calls `measure()` — a synchronous rect read — see Decided.
- `core/markup.ts` — build-or-verify markup: adopts existing `#arts-cursor` markup when present, otherwise builds the canonical tree (flat: every content part centers itself on the 0×0 wrapper anchor — no intermediary wrapper divs).

Injectables via `ICursorOptions`: `ticker` and `root`. `ITickerAdapter` is shape-compatible with tempus and with `@arts/component-runtime`'s `ITicker` (same callback, same optional `priority`/`label`), so a host that owns the frame loop can share it — obtainable from a foreign bundle as `window.__artsEngine__?.use(Symbol.for('engine/ticker'))`, the `Symbol.for` token identity being deliberate on that side. Only `deltaTime` and `frameCount` are portable across implementations: an injected ticker's `time` may count from its own clock epoch (tempus does), which is why `pipeline.frame` doesn't take it at all — `follower/motion.ts` drops it at the ticker boundary. It is also the seam the frame path is tested through — stepping an injected ticker makes frame-by-frame behavior deterministic. Discovery: boot installs `window.artsCursor` at parse time and resolves its `ready` promise once `init()` returns — touch-only included, where the engine comes up with its listeners detached; a deactivated plugin enqueues no script, so the global never appears at all. The engine also dispatches `arts-cursor:ready` on the document.

The docs site imports the engine only through the `@engine` alias (→ `src/ts/index.ts`) and styles through `@styles/*` — declared twice on purpose: tsconfig `paths` for the editor/typecheck, `docs/.vitepress/config.mts` for the browser build. Demo snippets in `docs/demos/` are single-sourced: the same file feeds the live render (`?raw` import) and the displayed code block (`<<<` include), and snippets show markup only — presentation lives in the theme's `demos.css`.

## Decided — don't reintroduce or "fix"

- WAAPI retargeting mode: rejected after a live feel comparison (rationale in the `follower/pipeline.ts` header).
- Magnetic engage measures fresh (`geometry.measure()`, not `resolve()`): page-space coordinates are scroll-invariant only for in-flow elements — a fixed or stuck-sticky anchor (Velum's sticky-header burger) is stale by the whole scroll delta, which rendered the first engage frames toward the old position and inflated the release radius. Engage already flushes style via `getComputedStyle().transition`, so the one rect read there is deliberate — don't "optimize" it back to the cache.
- `linear()` easing token: deliberately a cubic-bezier back-out instead — an unsupported easing arriving through `var()` silently kills the whole transition.
- **Two easing curves, not one.** `--arts-cursor-collapse-ease` is the back-out with the back removed (same x-timing, y flattened 1.56 → 1), and it exists because the back-out peaks at ~1.098: a `scale` transition to a target of exactly 0 interpolates `S * (1 - f(t))`, which goes NEGATIVE the moment `f(t) > 1`, and `scale` — unlike `opacity` or `width` — has no clamp, so the element mirrors back into view instead of hiding (measured: min −0.097, a 5.8px flipped ring for ~130ms of the 250ms). Don't collapse the two curves back into one, and don't reach for `scale: max(0, …)` — math functions resolve at computed-value time on the endpoints, so the overshoot is applied afterwards, unclamped. Which curve applies is pure CSS: a transition takes its timing function from the **after-change style**, so the collapsed-state rule carries `$motion-collapse` and the expanded-state rule carries `$motion`, and the direction switch costs no JS. For the wrapper and the press dot the collapsed state IS the base rule; the follower needs `data-cursor-collapsed` (`effects/suite.ts`, on `scale === 0`) only because its zero arrives as a number in a custom property and no selector can read one.
- The six public theming vars (`--arts-cursor-size`, `-text-color`, `-loading-color`, `-border-width`, `-border-color`, `-background-color`) are deliberately NOT registered via `@property` — registration would give them permanent initial values and silently disable the `var(--x, fallback)` theming pattern the styles are built on.
- Cross-navigation position restore: dropped.
- The scroll offset comes from `window` and nothing else — don't add a `scrollSource` injectable. `interaction/geometry.ts` derives page coordinates as `rect + window.scroll`, and the frame path subtracts `state.scroll` (a plain field `core/frameState.ts`'s `createScrollReader` keeps current by sampling `window` on a passive `scroll` listener — seeded once, re-synced authoritatively at engage and snap — so no per-frame `window.scrollX` forces layout; that listener is the same `window` sampled at a different moment, not a second source). A second source can only disagree with the first, and a rect already reflects the *applied* scroll while a smooth scroller reports the position it is animating toward. `@arts/smooth-scrolling` runs Lenis in native mode (`wrapper`/`content` never overridden, so it writes real `window.scrollTo` every frame), and there are no plans to support scroll-hijacking libraries that would need an adapter. `window.artsSmoothScrollingForElementor.lenis.scroll` is reachable on a Velum page and is exactly the value not to feed back in.
- `import.meta.env?.DEV` uses optional access on purpose: Vite defines it in the docs site, esbuild `define` substitutes it in plugin builds, `?.` keeps it safe in any bundler without the define.
- Splitting `src/ts/core/options.ts`: `fallow health --targets` recommends it on churn × fan-in and will keep doing so. Rejected — the file exists precisely so each default is stated once and shared by the initial resolve and the live patch. Its dependent count is also inflated by the test files that import `resolveOptions` to build fixtures. `fallow health` also flags `core/input.ts` on the same churn × fan-in heuristic — same rejection (a tiny file, and `accepts` belongs next to the listeners it gates).
- Splitting `effects/suite.ts`: the pure deciders and the applier co-evolve (a new payload key touches both), and the test tiers already split along the seam (`suite.test.ts` node / `suite.dom.test.ts` dom). Extract an over-threshold decider to module scope when fallow flags one (`arrowOnlyPill` is the worked example) — don't split the file. Revisit only if it keeps growing.
- **`hint` vs `label` is a deliberate split, not drift.** `label` is the payload key holding the TEXT; `hint` is the thing the cursor becomes while showing content. So `data-cursor-hint` is raised for an icon-only payload too, `--arts-cursor-hint-*` styles the pill/circle/icon alike, and `.arts-cursor__hint` contains `__hint-text` and `__hint-icon`. Names that stay `label` on purpose: the payload key, the per-widget wording vars `--arts-cursor-{drag,media,box,image,card}-label` and their controls, `sanitize_hint_label`, `readCssLabel`/`labelVar`, the `'label'` enum value meaning "text not icon" in the Content chooser, and the unrelated ticker `label` option.
- The standalone icon (`className` payload key → `.arts-cursor__icon` → `data-cursor-icon`) was deleted pre-1.0: fully implemented and unit-tested, but never used by `Options.php`, `WidgetControls.php` or any demo, and no shipped CSS gave that element visible content. Icons ride the hint's icon slot (`icon`/`iconClass`/`iconUrl`) — don't add a second icon channel back.
- `highlight.opacity`: rejected, not merely unimplemented. `.arts-cursor__follower` is a leaf (label/icon/arrows/dot are its siblings), so element opacity could only touch its own fill and border — which two rgba controls already do independently, and `background-color`/`box-shadow` are already in its transition list while `opacity` is not. A single opacity knob would be strictly less expressive.
- One Site Settings section per visual state. "Text Hints" and "Icon Hints" were merged into **Hints** because they weren't peers: a hint can be text AND icon at once (`data-cursor-icon-kind` means "has an icon", not "is an icon"), so the second section was a base+override pair whose 8 duplicated controls wrote the *same* vars one attribute tighter — invisible inheritance Elementor can't render for sliders or colors. Per-icon styling stays reachable in CSS via `.arts-cursor[data-cursor-icon-kind]`.
- `data-cursor-shape-axis` keeps `'x'|'y'` while `arrows` keeps `'horizontal'|'vertical'` — different questions (which dimension the pill's box stretches vs which arrow pair the author asked for), consumed by disjoint code. Unifying the spelling would imply a relationship that isn't there.
- The cursor over an `<iframe>`: the parent document goes blind while the pointer is INSIDE one — cross-origin embeds (YouTube/Vimeo/Maps) are out-of-process under Chrome site isolation, so no pointer events and no `:hover` reach the parent from over the frame (verified live; only `elementFromPoint` still resolves it). What ships rides the one observable signal instead: the crossing INTO the frame is the last parent-side event and `pointerover` targets the iframe element, so `resolveTarget` returns null for an iframe (no rule may hold, `refresh()` included) and the move gate in `createCursor.ts` folds the engine back to the not-yet-seen state — the ring collapses away and re-materializes at the pointer on the next parent-side event, like page entry. The rejected workarounds stay rejected: an overlay injects DOM over third-party embeds and blocks their interaction; a geometry/idle watchdog is heuristic and misses fast flicks; `pointer-events: none` kills interaction. Don't "upgrade" this to tracking or restoring within the frame — nothing is observable in there, and hiding is also the honest answer (the embedded document owns the native cursor over its own pixels; anything we drew there would be a second cursor).

## Elementor integration — landmines (verified in source; don't re-derive)

Each of these cost real debugging time and none of them fails loudly. `src/php/Elementor/WidgetControls.php` injects the per-widget "Cursor Effects" section; `Options::build()` holds the selector→effect rules.

- **Per-instance data reaches the cursor as a marker class or a CSS var — never an attribute.** Neither editor render path populates `_wrapper` (the JS-template path builds the outer node client-side; the AJAX path calls `render_content()` directly, never `print_element()`), so a PHP-printed attribute is correct on the front end and invisible in the preview. Enable/disable therefore *must* be a class (it has to participate in a selector the engine matches with `closest()`); text and icons *must* be a var via `selectors`.
- **Nothing riding `selectors` may contain a `;`.** Elementor splits every declaration block on `;` and silently discards the **whole block** as soon as a fragment has no `:` left in it (`Stylesheet::add_rules`) — no warning, no partial output, the widget's rule simply never gets written. A base64 data URI carries `;base64` in its own header, which is why the icon SVG is `rawurlencode`d (`inline_font_icon_svg`), and why typed hint text has `;`, `"` and `\` stripped (`sanitize_hint_label`). Blast radius is one `add_rules` call, so neighbouring controls survive — but anything we ever put through `selectors` has to clear this.
- **A CSS escape is not the way around it**: `getComputedStyle` returns `"a\3B b"` with the escape **unresolved**, so the cursor would render the escape sequence itself. Strip, don't escape.
- **`get_controls()` hides controls that carry `selectors` outside the editor.** They're diverted to a separate `style_controls` bucket whenever `Performance::should_optimize_controls()` — which is just `! is_admin() && ! is_preview_mode() && ! REST_REQUEST`, i.e. *always* on the front end, gated by no experiment. So a front-end probe reporting a control as "not registered" proves nothing; flip `Performance::set_use_style_controls( true )` around the read first.
- **Verify every selector against the RENDERED front-end page, not the widget source.** `.elementor-clickable` is the standing example: Image and Media Carousel both add it only under `is_edit_mode()`, so a rule keyed on it matches in the preview and never once on a real page.
- **A widget's "last Style section" is a byproduct, not a contract** — `start_injection()` re-splices the controls array, so the section registered last in source routinely isn't last in the stack. Measure it off the registered stack (iterate `get_controls()` for `type === 'section'`, ignore the `_section_*` Advanced ones); reading Pro's Testimonial Carousel source puts its last section one place too early.
- **We never enqueue Font Awesome** — Elementor does it for us because ours is an ICONS control (its `icons_fonts[]` bookkeeping fires on control TYPE, before the `selectors` check). The one gap: with `e_font_icon_svg` active it stops loading the webfont on the **front end only**, which is exactly what the data-URI channel in `inline_font_icon_svg()` covers. Both states are verified live.

## Conventions

- Formatting is Biome's: 2-space indent, single quotes, no semicolons, no trailing commas, 100-col lines.
- Commits: `domain: lowercase summary` (`engine:`, `magnetic:`, `styles:`, `types:`, `scaffold:`, ...), body in prose explaining why.
- TypeScript is `strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` (several internal records are typed required-but-possibly-undefined to forward optional fields verbatim — see `ICompiledRule`); the package's `types` entry points at `src/ts/index.ts` directly (no emitted d.ts).
- Pure module-scope helpers are exported even when nothing in the repo imports them (`resolveAppearance`, `parsePayload`, `ruleEnabled`, `writeEntry`, …). They are the unit-test surface, not dead code — don't "clean them up" as unused. A module export is internal by convention; the package's public API is whatever `src/ts/index.ts` re-exports.
- Tests live in `tests/ts/`, a tree mirroring `src/ts` (PHP suites would go to `tests/php/`, e2e to `tests/e2e/`), not colocated — colocation doubles every source folder's listing. They import the engine through the `@ts/*` alias (tsconfig `paths` + vitest `resolve.alias`), plus shared fixtures from `tests/ts/support.ts` relatively. The alias is TEST-ONLY: a `@ts/` import inside `src/ts` would force the mapping onto every consumer compiling the source (Velum does), which is why `tests/ts/aliasBoundary.test.ts` greps the shipped tree and fails the suite on the first leak. Tests are covered by `tsconfig.json`'s `include` and Biome's `files.includes`, and never shipped (release staging copies only `src/wordpress-plugin`, `src/php` and `vendor-prefixed`; esbuild bundles from `boot.ts`, so a test file is unreachable either way).
- Test conventions: import from `vitest` explicitly rather than enabling globals, so `tsconfig.json#types` stays `["node"]`. Fake collaborators with plain object literals, not a mocking library — the engine never uses `instanceof` (that is what `utils/isElement.ts` is for), so `{ nodeType: 1, closest: () => null }` is a legitimate Element to every consumer, and a `{ resolve: vi.fn() }` is a legitimate geometry cache. Name each `it` after the rule it protects. Copy vectors into a fake state rather than aliasing a shared literal: the frame path mutates `state.lag`/`state.follower` in place, so an aliased fixture leaks across tests.
- `tests/ts/phpDefaultsParity.test.ts` is the one test that reads PHP: it regex-parses `Options::build()`'s `size_of()` fallbacks and `is_on()` defaults and asserts they equal `constants/defaults.ts`. The two languages share no build step, and a default changed on one side only ships as "the editor preview disagrees with the published page" — PHPStan is type analysis and can't see a value drift, and nothing else in the suite opens a `.php` file. So **changing a default in `Options.php` means changing `defaults.ts` in the same commit**, or this fails. It parses rather than executes on purpose: booting WordPress for a handful of numbers isn't worth a PHP runtime in the suite.
- `coverage.include` is set explicitly in `vitest.config.ts` because v4 removed `coverage.all` and otherwise reports only files touched by a run — an untested module would be absent rather than showing as 0%. Related trap: `coverageConfigDefaults.exclude` is an empty array in v4, so the `[...coverageConfigDefaults.exclude]` idiom still found in older guides silently contributes nothing; the exclude list is written out in full. No thresholds — the few remaining uncovered branches are type-mandated guards unreachable by construction, and the visible behavior lives in the CSS state machine and real layout that coverage cannot measure, so a percentage gate would enforce nothing useful.
- Test environment: default to `node` and opt individual files into `happy-dom` with a `// @vitest-environment happy-dom` docblock. Probed against jsdom 29 / happy-dom 20: **jsdom has no `matchMedia`, `ResizeObserver` or `IntersectionObserver`**, so `createCursor().init()` throws there (at `createGeometryCache`, before it reaches the media query); happy-dom has all three and reports `(hover:hover) and (pointer:fine)` as matching, so the engine boots enabled. Most of the engine — the whole frame path, options, the scale grammar, the pure deciders — needs no DOM at all, and a `node` default makes an accidental `document` reach fail loudly instead of passing against a fake.
- Two tiers, and the environment is per FILE, so a module with both gets two: `x.test.ts` holds the pure deciders under `node`, `x.dom.test.ts` the stateful/applier half under `happy-dom` (`suite`, `targets`, `magnetic`, `createCursor`, `geometry`). A module that is DOM-only end to end keeps one file and just carries the docblock (`core/markup`, `core/input`, `core/frameState`, `follower/transformWriter`, `effects/magneticSessions`); one that needs no DOM at all keeps one `node` file (`core/ticker`, `follower/motion`, and the rest of the `follower/` frame path). Don't merge a pure file into its DOM sibling to save a file — that is exactly the `node` guard above being thrown away.
- `import.meta.env.DEV` is forced **false** for tests by `tests/ts/setup.ts` (`vi.stubEnv`), so the dev-only branches — `parsePayload`'s `console.debug`, `ref()`'s missing-markup warn, `warnIfContainingBlockHijacked`'s deferred rAF — do not run, and the suite exercises the code that ships. A `define` cannot do this job: Vite matches the literal `import.meta.env.DEV` member expression and every call site writes `import.meta.env?.DEV`, so a `define` in `vitest.config.ts` would silently do nothing (esbuild *does* substitute the optional chain, which is why the plugin bundle is unaffected either way). The tests that cover those three branches flip it back with `vi.stubEnv('DEV', true)` for their own scope and restore false afterwards; everything else runs the shipped path.
- Don't add injectables for what a test can stub. `createGeometryCache` constructs its own `ResizeObserver`/`IntersectionObserver` on purpose: `vi.stubGlobal` with a fake that captures the callback drives records synchronously, which is what makes eviction, streaming re-observe and the resize debounce assertable. Same for the ticker's rAF, and for the suite's base size (`offsetWidth` is 0 in every non-browser DOM, so scales resolve against `BASE_SIZE_FALLBACK` unless the test defines the property). Injected observers could not desync anything the way `scrollSource` could, but they would still be configurability nobody asked for.
- Some things unit tests structurally cannot reach, and the docs site (`pnpm dev`) is the harness for them: real layout and hit-testing (every rect is 0×0) and the CSS state machine that owns most of the visible behavior. The CSS Typed OM branch in `follower/transformWriter.ts` sits near that line: no non-browser DOM implements it, so the suite drives it through stub constructors that reproduce the CSSMatrixComponent copy trap, and the docs site remains the check against the real API (the matrix math and dedupe are shared with the string fallback — don't extract them, it would allocate on the frame path).
- Interfaces, type aliases, and constants live in dedicated folders (`src/ts/interfaces`, `src/ts/types`, `src/ts/constants`) — one declaration per file, `I`-prefixed interfaces, `T`-prefixed types, each folder with an `index.ts` barrel. Modules import them back through the barrel (`../interfaces`, `../types`, `../constants`); `src/ts/index.ts` re-exports the public names. Declaration files import other declaration files directly (`./IX`, `../types/TX`), never through the barrels — routing `interfaces/ → ../types` through the barrel would close a `types/index ↔ interfaces/index` cycle via `TBootOptions`; the barrel rule applies to consumer modules. The ambient global augmentations keep their exact built-in names, not `I`-prefixed (prefixing breaks declaration merging): `Window` in `global.d.ts`, `ImportMeta` in `env.d.ts`, `SymbolConstructor` co-located with its consumer in `interfaces/ICursorSession.ts`.
